用户想知道"上下文里装了什么"。先分清该用哪个工具：

- **绝对 token 构成**（消息 / 系统工具 / MCP 工具 / 技能 / 系统提示词各占多少）→ 让用户看 ZCode 内置的
  **「上下文容量」面板**。它用客户端自身记账，分母就是本次请求的 `input_tokens`，是权威来源。
  本插件**刻意不估算**这个：用单一全局密度估算静态部分实测差 1.85 倍，改做最小二乘反解又因样本区间
  太窄而病态。不要把插件的字符量换算成 token 报给用户。
- **这些 MCP 工具定义分别来自哪个服务器**（面板给不了）→ 调用 MCP 工具 `spend_context_breakdown`
  （`session_id` 可选）。

汇报时必须带上的口径说明：
- 输出的是**精确字符量**（逐条实测，并已校验在整个会话内恒定），不是 token 估算。
- 占比在**同一类内容内部**计算，token 密度会约掉，因此不依赖任何分词假设。
- `model-io` 是**滚动窗口**：`retainedRequests` 只代表最近保留的请求数，不等于会话请求总数；
  静态构成在同一会话内恒定，故测量本身不受窗口影响。
- 若 `consistency.toolsCharsStable` 为 false，说明会话中途工具集变了（MCP 重连或插件启停），
  这本身是有用信号，要告诉用户。

最有价值的结论是「哪些 MCP 服务器占工具定义最多、其中哪些在窗口内从未被调用」。
但要把取舍讲清楚：这部分内容常驻缓存，**美元影响很小**（约为新增输入的 1/41），
真实收益是上下文窗口占用与长会话余量，而不是立刻省下多少钱。
